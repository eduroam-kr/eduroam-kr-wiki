로밍 대시보드에 거절이 쌓이면 공격처럼 보이지만, 대부분은 설정이 틀린 단말 몇 대가 계속 다시 시도한 결과입니다. 이 문서는 로밍 서버가 옆 서버를 막지 않는 이유와, 거절을 읽고 줄이는 방법을 정리합니다.

## 인접 서버 신뢰 원칙

- 로밍 서버는 바로 옆에 붙은 서버(NRO, RO, 해외 ETLR)를 믿어야 동작합니다. ETLR(European Top-Level RADIUS)은 나라 사이의 요청을 중계하는 최상위 서버입니다.
- 옆 서버를 막으면 한 사용자가 아니라 그 뒤에 연결된 기관 전체가 끊깁니다.
- 실패가 많다는 것만으로 악성인지 판단할 수 없고, 판단해서도 안 됩니다. 흔한 원인은 다음과 같습니다.
    - 비밀번호 입력 실수, 비밀번호 만료
    - EAP 방식, 인증서, realm 같은 설정 오류
    - 실패한 단말의 자동 재시도. 재시도 횟수는 그 단말의 문제입니다.

## 거절 응답의 해석

- 거절 패킷의 Reply-Message(RFC 2865, 타입 18)는 거절한 서버가 쓴 문구입니다. 중계 서버는 바꾸지 않고 전달하므로, 「Request Denied」 같은 문구는 대개 해외 중계 서버나 홈 IdP 가 보낸 것입니다. 누가 거절했는지는 패킷 캡처나 중계 서버의 상세 로그로 확인합니다.
- NRO 가 직접 거절하는 것은 라우팅할 수 없는 realm 입니다. `*.local`, `*.guest` 처럼 실제 도메인이 아닌 realm 과 도메인 오타가 여기에 해당합니다. NRO 는 오타가 흔한 realm 에 올바른 realm 을 Reply-Message 로 알려 줍니다.
- 거절을 (사용자, 단말 MAC) 쌍으로 묶어 보면 기간 내 성공이 한 번도 없는 쌍이 거절의 대부분을 차지합니다. 한 단말이 시간당 백 회 넘게 시도하는 경우도 드물지 않습니다.
- 홈 IdP 의 거절은 국내 중계 서버에서 고칠 수 없습니다. 원인은 그 사용자와 그 소속 기관에 있습니다.

## 반복 실패 감소 방안

- AP 와 무선 컨트롤러에서 반복 실패 단말을 일정 시간 제외(client exclusion)합니다. 거절 로그와 해외 트래픽이 함께 줄어듭니다.
- 익명 ID 를 쓰는 단말은 모두 `anonymous@realm` 으로 보이므로, 사용자 단위로 나눠 보려면 단말 MAC(Calling-Station-Id)과 CUI 를 함께 봅니다([익명 ID 와 realm]({{ '/tech/identity-and-realm/' | relative_url }})).
- 실패 탐지와 계정 잠금은 홈 IdP 가 합니다([계정 · 비밀번호와 EAP 방식]({{ '/tech/credentials/' | relative_url }})).

## NRO · RO 간 라우팅

NRO 와 RO 는 서로 넘기는 realm 을 정확히 일치하는 이름이나 정규식으로 정합니다. FreeRADIUS 는 정확히 일치하는 realm 을 먼저 고르고, 없을 때만 정규식 realm 을 설정한 순서대로 검사하며, 그래도 없으면 DEFAULT 를 씁니다. 목록에 없는 realm 을 서로 되돌려 보내면 요청이 두 서버 사이를 맴돌므로, 받은 쪽은 자기 목록에 없는 realm 을 거절합니다([RO 운영 요건]({{ '/rules/ro/' | relative_url }}) 1.3).

실제 구성 예는 [kr-nro-docker](https://github.com/eduroam-kr/kr-nro-docker) 에 있습니다.
